# 주석 · 문서화

Clean Code · Effective Java 의 주석 관례를 따른다.  
코드 자체로 의미가 전달되도록 작성한다.

> **불필요한 주석·Javadoc·`@Schema` 는 절대 작성하지 않는다.**  
> 주석이 과하면 오히려 코드를 읽기 어려워진다. 확신이 없으면 쓰지 않는다.

## 원칙

- 주석은 기본적으로 쓰지 않는다. 아래 규칙에 해당할 때만 예외로 쓴다.
- 무엇을 하는지보다 **왜 그렇게 처리하는지**를 설명한다.
- 이름·구조로 드러낼 수 있으면 주석 대신 이름·구조를 고친다.
- 코드를 그대로 읽어 주는 주석, 변경 이력·작성자 주석은 쓰지 않는다 (이력은 git).

## DTO 필드

| 대상 | 규칙 |
| --- | --- |
| 일반 DTO 필드 | 필드명으로 의미를 알 수 있으면 주석을 쓰지 않는다 |
| API DTO 필드 | 의미나 계산 기준이 불명확하면 `@Schema(description = ...)` 로 설명한다 |

```java
// 좋음: 계산 기준이 이름만으로 드러나지 않는다
@Schema(description = "허용 초과 입고율(%). 발주 수량 대비, 0~100")
BigDecimal overReceiptPct
```

## 검증

| 대상 | 규칙 |
| --- | --- |
| 단순 검증 | `@NotNull`, `@Positive`, `@Size` 등 Bean Validation 을 쓴다 |
| 복잡한 검증 | 필드 간 관계·조건부 검증은 커스텀 Validator 로 분리하고 **테스트를 작성한다** |

- 커스텀 Validator 는 제약 어노테이션 + `ConstraintValidator` 구현으로 둔다.
- 검증 규칙을 주석으로 설명하지 않는다. 어노테이션과 Validator 이름이 규칙을 드러내게 한다.

## 비즈니스 규칙

- 복잡한 업무 규칙은 클래스·메서드 **Javadoc** 또는 `docs/features/<도메인>/` 문서로 관리한다.
- 여러 클래스에 걸친 규칙은 문서에 두고, 코드에는 문서 링크만 남긴다.

## Service 로직

- 코드만으로 의도를 파악하기 어려운 부분에만 `//` 주석을 쓴다.
- 예: 순서가 중요한 이유, 의도적으로 예외를 무시하는 이유, 동시성·성능 때문에 택한 방식.

```java
// FK 순서: purchase_order → revision → line
purchaseOrderRepository.save(po);
```

## 체크리스트

- [ ] 지워도 이해에 지장 없는 주석이 남아 있지 않은가?
- [ ] 주석이 "무엇"이 아니라 "왜"를 설명하는가?
- [ ] 이름만으로 충분한 필드에 주석·`@Schema` 를 붙이지 않았는가?
- [ ] 불명확한 API DTO 필드에 `@Schema` 설명이 있는가?
- [ ] 필드 간·조건부 검증이 커스텀 Validator 로 분리되고 테스트가 있는가?
- [ ] 복잡한 업무 규칙이 Javadoc 또는 `docs/` 에 정리되어 있는가?
