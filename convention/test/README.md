# 테스트

Test Pyramid · JUnit 5 관례를 따른다.

## 종류

| 종류 | 대상 | 비고 |
| --- | --- | --- |
| 단위 | 서비스·도메인 로직 | 외부는 mock |
| 슬라이스 | 컨트롤러·매퍼 | `@WebMvcTest` 등 |
| 통합 | 주요 흐름 + DB | 실제에 가깝게 |

- 단위가 가장 많고, 통합은 중요한 경로만 (피라미드).
- getter만 있는 코드·프레임워크 동작을 테스트로 채우지 않는다.

## 이름·구조

- 클래스: `{대상}Test` / 통합은 `{대상}IT`
- 메서드 이름 또는 `@DisplayName`으로 **무엇을 보장하는지** 드러낸다.
- given / when / then (또는 arrange / act / assert)로 구간을 나눈다.
- 테스트 하나 = 검증 포인트 하나.

## 규칙

- 네트워크·실제 시계·`Thread.sleep`에 의존하지 않는다. 필요하면 추상화·고정 시계.
- 테스트끼리 순서를 가정하지 않는다. 데이터를 공유해 오염시키지 않는다.
- mock은 외부 경계(DB 클라이언트·HTTP 클라이언트)에만 쓴다. 내부 호출 순서 검증에 집착하지 않는다.
- 버그 수정 시 **재현 테스트를 먼저** 작성한다.

## 실행

- PR 전에 변경 모듈 테스트를 로컬에서 돌린다. 못 돌렸으면 PR에 이유를 적는다.
- CI가 빨간 채로 병합하지 않는다.

## 체크리스트

- [ ] 경계값·예외 경로가 있는가?
- [ ] flaky 요소(sleep·공유 상태)가 없는가?
